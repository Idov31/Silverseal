# Repository Guidelines

## Project Structure & Module Organization

This repository contains the `no_std` UEFI bootkit in `silverseal-bootkit/`, with architecture assembly under `asm/<arch>/`. ARM64 uses a pinned profile generated by `silverseal-arm64-tool` and detours the stock zboot path; there is no second wrapper EFI binary. The Kbuild-managed module is in `silverseal-rootkit/`; `silverseal_rootkit.rs` is the real module while `src/lib.rs` is an IDE stub. The local logger fork is in `vendor/com_logger/`. Environment and VM helpers live in `scripts/`; `resources/` and `silverseal.yara` hold diagrams, branding, and detection rules.

## Build, Test, and Development Commands

- `cargo fmt --all -- --check` verifies Rust formatting without changing files.
- `cargo build-bootkit-x64 --release` builds x86 UEFI; `nasm` must be on `PATH`.
- `cargo build-bootkit-arm64 --release` checks the AArch64 UEFI path. Set `SILVERSEAL_ARM64_PROFILE=/absolute/path/fixture.ssarm64p` only for an exact pinned fixture; an omitted profile fails closed.
- `make -C silverseal-rootkit ARCH=arm64 KDIR=/path/to/build` builds the real ARM64 module; use `ARCH=x86_64` for x86.
- `cargo check -p silverseal-rootkit` validates the IDE stub only; it does not produce a loadable module.
- `cargo test-arm64` runs the consolidated ARM64 profile, detour, and trampoline contract tests.
- `cargo test -p silverseal-bootkit --bin silverseal-arm64-tool --features arm64-tools` tests profile creation.

## Coding Style & Naming Conventions

Use Rust 2024 conventions and standard `rustfmt` output with four-space indentation. Name functions and modules with `snake_case`, types with `CamelCase`, and constants with `SCREAMING_SNAKE_CASE`. Keep unsafe code narrowly scoped and document the relevant firmware or kernel invariant. Preserve SPDX license headers on kernel-facing files.

## Testing Guidelines

There is no automated test suite or coverage threshold. Before submitting, run formatting and the relevant build commands above. Validate bootkit, EFI, and kernel-module changes in a disposable VM; capture serial output or kernel logs for behavior that cannot be exercised by Cargo.

## Commit & Pull Request Guidelines

Follow the existing short, imperative commit style, for example `Fix rootkit loading`; Conventional Commits are not required. Keep commits focused. Pull requests should explain the change and risk, list exact validation commands and results, link applicable issues, and include screenshots or log excerpts for boot-flow or serial-output changes.

## Security & Configuration

Review scripts before running them with `sudo`. Deployment helpers replace EFI/GRUB files and can leave a system unbootable. Use disposable VMs, confirm kernel/header versions, and never commit private keys, credentials, or machine-specific artifacts.
